# The Bimodal Biometric Warehouse
### Mining Wearable and Nutritional Data for Metabolic Optimization

A full end-to-end data-science project that predicts **physiological recovery**
and **caloric expenditure** for "bimodal" activity profiles — days of intense
exercise (heavy dumbbell training or high-incline walking) followed by highly
sedentary recovery periods.

## Key Design Decisions

### Part 1 — Surrogate Keys + `pd.merge()` Integration

The two raw sources are kept completely separate, mimicking a real data-integration pipeline:

| Source | File | Key |
|--------|------|-----|
| Fitbit-style wearable export | `wearable_raw.csv` | `full_date` |
| MyFitnessPal-style meal log  | `nutrition_raw.csv` | `full_date` |

`load_data.py` aggregates each source independently, then calls `pd.merge()` on `full_date` to combine them. **Surrogate keys** (`date_sk`, `workout_sk`, `nutrition_sk`) are assigned *after* the merge, so the schema can handle multiple workout sessions per day without natural-key collisions.

### Part 2 — PCA on the 365 × 1440 Minute-Level HR Matrix

Instead of summarising heart rate to a single daily mean, the wearable export is pivoted into a **365 × 1440 matrix** (one row per day, one column per minute 0–1439). PCA applied to this matrix extracts *waveform* features:

| Component | Interpretation |
|-----------|---------------|
| **PC1** | Overall daily exertion (high loadings at workout-minute windows) |
| **PC2** | Bimodal vs. flat signature (distinguishes morning-workout + afternoon-walk from sedentary) |
| PC3–PC5 | Timing shifts (early vs. late workout start time) |

These 5 HR waveform components are included as features in all downstream models.

### Part 3 — Lag Features in Classification

The Random Forest / SVM classifiers receive **yesterday's** biometrics as explicit lag features:

```python
lag1_sleep           # yesterday's sleep duration
lag1_active_calories # yesterday's active calorie burn
lag1_hrv             # yesterday's HRV score
```

The Apriori step binarises *all* features including `YesterdayHighCal` and `YesterdayGoodSleep` transaction items.

### Part 4 — Full Pipeline Serialisation

Every sklearn Pipeline bundles a fitted `StandardScaler` together with the model. A single `joblib.dump(pipeline, ...)` call serialises both:

```python
rf_pipeline  = Pipeline([("scaler", StandardScaler()), ("clf", RandomForestClassifier(...))])
reg_pipeline = Pipeline([("scaler", StandardScaler()), ("lr",  LinearRegression())])
```

The Flask API calls `pipeline.predict(raw_input)` — scaling is applied automatically inside the pipeline, eliminating any risk of serving unscaled predictions.

## Star Schema

```
              ┌─────────────────────────┐
              │        Dim_Date          │
              │  date_sk  (surrogate)    │
              │  full_date (natural key) │
              └────────────┬────────────┘
                           │
┌──────────────────┐ ┌─────┴──────────────────────────────┐ ┌──────────────────┐
│   Dim_Workout    │ │     Fact_Daily_Biometrics           │ │  Dim_Nutrition   │
│ workout_sk  PK   │─│  fact_sk  PK  (surrogate)          │─│ nutrition_sk  PK │
│ full_date   (NK) │ │  date_sk  FK → Dim_Date             │ │ full_date   (NK) │
│ workout_type     │ │  workout_sk  FK → Dim_Workout       │ │ meal_category    │
│ intensity        │ │  nutrition_sk FK → Dim_Nutrition    │ │ protein_g        │
│ duration_minutes │ │  hr_pc1..hr_pc5 (HR PCA waveform)  │ │ is_high_protein  │
└──────────────────┘ │  lag1_sleep/active_calories/hrv     │ └──────────────────┘
                     │  recovery_score / recovery_label    │
                     └────────────────────────────────────┘
```

## Analysis Pipeline

| Part | Phase | Technique | Key Detail |
|------|-------|-----------|------------|
| 1 | Data Engineering | SQLite star schema, SQLAlchemy | Surrogate keys; `pd.merge()` on `full_date` |
| 2 | PCA on HR | 365 × 1440 waveform matrix | PC1=exertion, PC2=bimodal signature |
| 2 | EDA | Histograms, heatmap, protein→RHR | Mean imputation for sensor dropouts |
| 3 | Clustering | K-Means (k=3) | HR-PC features used as cluster inputs |
| 3 | Assoc. Rules | Apriori | Full binarisation + lag flags in transactions |
| 3 | Regression | `Pipeline([scaler, lr])` | RMSE & R² for calorie prediction |
| 3 | Classification | `Pipeline([scaler, rf])` + `Pipeline([scaler, svm])` | Lag features + HR PCA included |
| 4 | Evaluation | Confusion matrix, F1, ROC-AUC, RMSE, R² | Both classifiers benchmarked |
| 4 | Deployment | Flask REST API | Raw input → pipeline scales automatically |

## Deployment — Flask API

Start the server (requires running the notebook first to generate model artefacts):

```bash
python app/flask_api.py
```

**POST** `http://localhost:5000/predict`

```json
{
  "resting_heart_rate": 62,
  "hrv_score": 58,
  "sleep_duration_hours": 7.2,
  "protein_g": 180,
  "intensity": 7,
  "duration_minutes": 50,
  "total_active_minutes": 45,
  "active_calories": 350,
  "steps": 9500,
  "carbs_g": 210,
  "fat_g": 65,
  "is_high_protein": 1,
  "is_poultry": 1,
  "is_vegetarian": 0,
  "is_weekend": 0,
  "lag1_sleep": 7.5,
  "lag1_active_calories": 400,
  "lag1_hrv": 55
}
```

**Response:**

```json
{
  "recovery_label": 1,
  "recovery_probability_rf": 0.83,
  "recovery_probability_svm": 0.79,
  "message": "Ready to Train",
  "predicted_active_calories": 612.4,
  "note": "Input was raw (unscaled). Scaling applied inside each Pipeline."
}
```

Optionally include `"minute_level_hr": [<1440 floats>]` to supply the raw wearable export and have the API derive `hr_pc1`–`hr_pc5` automatically via the pickled HR PCA pipeline.
